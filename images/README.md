# Worker image recipes

OS recipes live independently of infrastructure adapters. The AWS adapter
composes its secure-bootstrap prerequisites with a Linux preparation script and
stores the recipe hashes beside the resulting AMI. Reuse these scripts from
other provider builders; keep cloud agents, licensing and capture in the adapter.

For Ubuntu MicroK8s workers, compose `linux/microk8s-prerequisites.sh` with the
provider's bootstrap preparation and use `linux/verify-microk8s-prerequisites.sh`
as the capture verifier. This shared layer installs snapd and Python 3 without
starting MicroK8s or capturing cluster identity. Native first boot installs the
explicit snap revision and consumes the join configuration. This prerequisite
layer does not claim a cached MicroK8s runtime or eliminate its startup download.

`linux/nvidia-ubuntu.sh` installs the Ubuntu 24.04 NVIDIA 580.173.02 server driver
and host diagnostic tools. It records the resolved package inventory inside the
image. Complete a reboot, then run `linux/verify-nvidia.sh` before capture. The
acceptance script requires GPU enumeration and a successful NVENC encode. These
host checks have been exercised on an AWS T4 builder; they do not qualify
fractional vGPU/GRID machines or other clouds.

From the repository root, after the [AWS setup](../docs/aws.md):

```sh
python3 harness/e2e/aws/bake.py start --work-dir <private-run-directory> \
  --instance-type g4dn.xlarge \
  --prepare-script images/linux/nvidia-ubuntu.sh \
  --verify-script images/linux/verify-nvidia.sh
# Wait for preparation; reboot the recorded builder before capture.
python3 harness/e2e/aws/bake.py capture --work-dir <private-run-directory>
# After EC2 reports the candidate image available:
python3 harness/e2e/aws/bake.py promote --work-dir <private-run-directory>
```

Promotion approves the AMI for the isolated harness's worker policy. Production
promotion additionally requires fresh-image bootstrap, scheduled GPU workloads
and the lifecycle/isolation gates in [GPU workers](../docs/gpu-workers.md).
Windows recipes are described below; additional cloud capture adapters remain
to be implemented.

For a k0s image layer, stage the exact Linux worker artifact through the build
provider's transport, then run as root in an unjoined image-builder VM:

```sh
python3 prepare_k0s.py --artifact /private/k0s \
  --sha256 VERIFIED_ARTIFACT_SHA256 --version v1.36.2+k0s.0
```

Stage [prepare_k0s.py](linux/prepare_k0s.py) alongside the artifact. This common
systemd Linux step validates the hash and native version, installs `/usr/local/bin/k0s`,
and records `/etc/cloud-provisioning-image/k0s.json`. It rejects existing k0s
configuration, runtime state, services, or a different installed executable.
The k0s join pattern already skips its download when this version matches.
This layer does not install a service, unpack containerd, preload workloads, or
provide NVIDIA toolkit integration. Those require separate preparation and
fresh-VM acceptance; do not apply the k0s layer to other distribution images.
For Linux runtime-cache inputs, run
`python3 images/linux/stage_k0s_runtime.py --worker /path/to/k0s --sha256 VERIFIED_SHA256 --output /path/to/new-directory`
from the build host. The shared extractor selects Linux containerd, its runc
shim and runc, preserving their exact embedded bytes and marking ZIP entries
executable. The Windows entrypoint selects its own runtime filenames and file
modes through the same extractor. The
[Linux staging check](../docs/validation/linux-runtime-staging-results.json)
matches all three components against the installed binaries in a QEMU worker.
Staging creates `runtime.zip` and `runtime.json`. Transfer them and
[prepare_runtime.py](linux/prepare_runtime.py) into an unjoined Linux image
builder, then run as root:

```sh
python3 prepare_runtime.py --runtime-archive runtime.zip \
  --runtime-manifest runtime.json
```

Preparation independently compares all three components with the installed
k0s executable's embedded payload, then installs them under `/var/lib/k0s/bin`
with k0s's `0750` mode and exact executable timestamp. These values let k0s reuse
the staged files on startup. The helper rejects Kubernetes services, cluster
configuration and existing runtime stores. Run this layer before cache creation.
A completed repeat validates and preserves the original files and receipt;
an incomplete intent requires inspection of the original operation before any
recovery. The receipt is `/etc/cloud-provisioning-image/linux-runtime.json`.
This prepares runtime binaries; starting a temporary build runtime, importing
and unpacking container layers, and validating cloned-cache reuse are separate
steps. No distribution runtime configuration is generated by this helper.

Build the Linux cache on the unjoined VM after staging its runtime binaries:

```sh
python3 prepare_cache.py --recipe cache-recipe.json \
  --operation /var/tmp/cache-build-unique-id
```

Stage [prepare_cache.py](linux/prepare_cache.py), the recipe and any referenced
OCI archives together. Each image supplies either a digest-pinned `pullReference`
or an `archive` basename with `archiveSHA256` and its imported `reference`.
Declare the source and every workload spelling in `aliases`; those names must
resolve to the declared `digest`. The builder verifies archive hashes before
starting containerd and again before import. It refuses alias retargeting and
unexpected references.

The default cache root is `/var/lib/k0s/containerd`. Both that store and the
operation directory must be new; this command does not extend or replay an
existing cache. `--minimum-free-gib` defaults to 8 and is a preflight guard,
not an extraction-size estimate. `--cache-root` selects a separate store for
native builder testing; a scratch-store result does not prepare k0s's default
store for image capture. Existing Kubernetes services, cluster configuration or
running containerd processes prevent preparation.

The builder preserves its recipe, original process identities and per-command
logs, stops each runtime through its original process handle, and checks all
references before and after restart. Interrupted work retains its evidence and
partial cache for inspection. Copy operation evidence off the image and remove
staged archives before capture. Keep cloud credentials and provider capture
logic in the infrastructure adapter.

The [native public-builder checks](../docs/validation/linux-public-cache-builder-results.json)
exercise digest-pinned pulling, archive import, alias preservation, runtime
restart and refusal to replay an existing operation on a single-NIC AWS VM.
The [complete GPU-recipe build](../docs/validation/linux-full-public-cache-builder-results.json)
also exercises all twelve images and twenty-three runtime references, including
the selected init containers, dialer and first GPU workload. These are native
scratch-store checks on an unjoined CPU builder. Preparing the default store for
capture and qualifying a fresh GPU worker remain separate requirements.

Validate a prepared Linux cache with the independent
[native checker](../harness/e2e/observe/linux_cache_native.py). Stage it with
[linux_cache.py](../harness/e2e/observe/linux_cache.py) and a digest-pinned cache
recipe on the unjoined builder, then run:

```sh
python3 linux_cache_native.py --recipe cache-recipe.json \
  --operation /var/tmp/cache-acceptance-unique-build-id
```

The recipe requires `schemaVersion: 1`, `machineOS: linux`, `architecture: amd64`,
the installed `workerSHA256`, and an `images` array. Each image declares an
immutable `digest` and explicit `aliases` matching the workload's references.
Include selected DaemonSet init containers, the distribution's pause image, and
the first application workload. A tag alias must resolve to its declared digest;
pin the corresponding deployment input as well to avoid registry tag changes.

The checker verifies runtime hashes, modes and timestamps, then opens the
existing `/var/lib/k0s/containerd` store twice using the staged containerd. It
requires complete content and unpacked snapshots for every reference before and
after restart. It performs no pull, import or alias creation. Its temporary
configuration stays in the operation directory; it does not generate the
distribution's configuration or install Kubernetes services. Both original
runtime processes must exit before the check passes.

Retain the operation evidence outside the image. If interrupted, inspect that
operation and its processes before retrying in a new directory. A passing result
only accepts the builder cache. Image capture and a fresh CAPI worker must still
prove cache reuse before harness imports, application execution, and safe node
removal and replacement. Builder checks do not establish startup savings.
The [Linux cache capture evidence](../docs/validation/linux-gpu-cache-capture-results.json)
records the runtime/driver checks and independent cache acceptance separately
from fresh-worker qualification. For AWS, bind incremental acceptance using
`bake.py capture --capture-check` as described in [the AWS workflow](../docs/aws.md).

On a fresh Linux worker, inspect the cache before importing any harness images.
Resolve each pinned image's Linux amd64 manifest and config, hash its required
content blobs, and inspect the committed overlayfs snapshot chain derived from
the config's `rootfs.diff_ids`. Compare blob modification/change times and native
snapshot creation/update times with the provider's instance launch time. Compare
runtime hashes, inodes and change times with the capture receipt as well: matching
mtime alone does not prove that k0s skipped extraction. The
[reuse validator](../harness/e2e/observe/linux_cache_reuse.py) and its native fixture
implement these checks. This proves reuse of those cached artifacts; it does not
prove zero registry requests or reduced startup cost. Run the intended GPU
workload and lifecycle checks separately.
The [fresh AWS GPU cache result](../docs/validation/linux-gpu-cache-capi-results.json)
records blob and snapshot reuse, a GPU workload using its baked image, the
network matrix, node removal and diagnostic survivor failures as separate results.
Validate executable staging independently from image capture and fresh-worker
reuse. The [runtime preparation evidence](../docs/validation/linux-runtime-preparation-results.json)
covers the staged files and repeat behavior; the
[CPU CAPI evidence](../docs/validation/linux-k0s-baked-capi-results.json)
covers a fresh worker and removal. Neither replaces GPU cache, replacement or
survivor-traffic qualification. A diagnostic run remains unqualified even if its
own traffic samples pass.

To compose the GPU driver layer onto a captured Linux k0s layer, select that
parent explicitly when starting a new AWS builder:

```sh
python3 harness/e2e/aws/bake.py start --work-dir <private-run-directory> \
  --base-image-id <owned-linux-k0s-ami> --instance-type g4dn.xlarge \
  --prepare-script images/linux/nvidia-ubuntu.sh \
  --verify-script images/linux/verify-nvidia.sh
```

The parent must be private, available, owned by the run's account and tagged
for that run. The current Linux builder accepts x86_64 HVM images with one EBS
root disk, preserves its device name, and allocates at least its original size
(20 GiB minimum). Instance-store mappings in the parent are not counted as EBS
disks. The helper records `builderParent` without changing `baseAMIID` or the
default worker AMI. An existing builder cannot switch parents; finish or clean
up the original build first. Omitting the option retains the original base-image
behavior. Cloud bootstrap prerequisites still run during the image build.

Reboot the GPU builder and verify both the preserved k0s layer and native GPU
execution before capture. A composed image still needs fresh CAPI joining,
scheduled graphics/encoding, cache reuse, removal and replacement checks.
This option does not bake the NVIDIA toolkit or qualify a parent image by itself.
Use the [composed-image validation](../docs/validation/linux-k0s-gpu-image-capture-results.json)
for the driver/reboot acceptance criteria and the
[fresh GPU CAPI validation](../docs/validation/linux-k0s-gpu-baked-capi-results.json)
for joining and hardware execution. A manually imported workload image does not
prove startup cache reuse. Keep replacement and survivor-traffic results separate
from successful GPU rendering or encoding.

`probes/linux` builds a workload image with no startup package installation:

```sh
docker build -t cloud-provisioning/gpu-probe:linux-v1 images/probes/linux
```

The probe rejects a software Vulkan device, clears a 64×64 image on an NVIDIA
graphics queue, reads back and verifies every pixel, then encodes 30 frames with
NVENC. It writes a success record to Kubernetes' termination log only after both
operations succeed. This tests device/library injection and offscreen image
operations; it does not substitute for Unity rendering, shader performance or
an end-to-end stream. Schedule it on a GPU VM with a device allocation. Record
the built image digest, resolved package versions and output in test evidence.

Use [the pod template](probes/linux/pod.yaml), replacing the node selector and
image digest with the GPU node and your published image. Apply it using the
isolated test cluster's explicit kubeconfig. Require phase `Succeeded`, exit code
zero and the termination message containing `vulkanPixelsVerified: 4096` and
`nvencFrames: 30`. The GPU resource request exercises scheduler allocation and
CDI/NRI injection without privileged device mounts.

The workload image includes `libegl1` as well as the Vulkan loader. NVIDIA's
injected vendor libraries alone are insufficient: without the EGL loader the
tested driver failed `vkCreateInstance` even though its ICD was injected. Keep
these userspace dependencies in the image; do not install them at pod startup.

## Windows layers

The [Windows Calico image builder](calico/README.md) derives a container image
from a pinned upstream base and the validated Felix executable. This removes
the startup dependency on a manually staged host binary. The image can be
published to each cloud's OCI registry and preloaded during VM preparation;
machine licensing, GPU drivers and provider agents remain separate layers.

For k0s, use its existing [OCI bundle import path](https://docs.k0sproject.io/stable/airgap-install/)
when preparing offline image delivery. In the pinned 1.36.2 source, the worker
registers `OCIBundleReconciler` with its managed containerd on Windows as well as
Linux, reads `<data-dir>/images`, and imports into the `k8s.io` namespace. Do not
add a parallel bootstrap importer for this distribution. A staged archive still
requires import at startup; it is not evidence that Windows layers were unpacked
before capture. Validate a prepared runtime cache on both Windows builds through
Sysprep and a fresh CAPI boot before claiming that startup performs no image
downloads or layer extraction. The [Windows 2022 fresh-cache result](../docs/validation/windows-capi-gpu-startup-cache-canonical-2022-results.json)
and [Windows 2025 result](../docs/validation/windows-capi-gpu-staged-withdrawal-2025-results.json)
establish observed cache reuse after capture and fresh CAPI boot. Cache-hit events
and runtime inventory do not establish zero registry access or startup savings.

Prepare runtime inputs for that image-build work from the exact worker artifact:

```sh
python3 images/windows/stage_k0s_runtime.py \
  --worker /path/to/k0s.exe --sha256 VERIFIED_WORKER_SHA256 \
  --output /path/to/new-runtime-directory
```

This build-host command reads k0s's appended payload and emits a conventional
`runtime.zip` containing its containerd and Windows shim, plus `runtime.json`
with the worker, archive and component hashes. It rejects a changed worker,
missing or duplicate components, and an existing output directory. The build-host
ZIP conversion is required for the native Windows reader;
see the [runtime staging fixture](../docs/validation/windows-runtime-staging-results.json).
Staging does not change a running runtime. Pre-unpacking on an unjoined builder
and proving cache reuse after Sysprep remain separate requirements.

`windows/prepare-cache.ps1` builds that cache on a fresh, unjoined Windows VM.
Stage it beside `cache-runtime.ps1` and `inspect-cache.ps1`, together with the
runtime archive/manifest, the native unpack helper and a [cache recipe](../docs/windows.md#private-aws-image-capture).
Build the helper from `images/windows/cache-unpack` with
`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o cache-unpack.exe .`.
Run `go test -cover ./...` in that module for its host-side input checks; Linux
unit coverage excludes native Windows unpacking. Record the executable's SHA-256
on the build host and stage it with the scripts. The helper
uses containerd 2.3.2's native Windows matcher to unpack existing content; it
never contacts a registry or creates a workload. Local `ctr pull` wraps its
matcher in `platforms.Only()`, which loses Windows version preference ordering
in the pinned platforms library. Removing the bare platform override alone
fixed Calico CNI but left Konnectivity unready on the observed 2025 builder.

Invoke preparation with the staged file paths and recorded helper digest:

```powershell
.\prepare-cache.ps1 -RuntimeArchive .\runtime.zip `
  -RuntimeManifest .\runtime.json -Recipe .\cache-recipe.json `
  -UnpackHelper .\cache-unpack.exe -UnpackHelperSHA256 SHA256
```

The common script verifies the worker/runtime inputs, stages k0s's embedded
runtime, and pulls and unpacks the pinned images into its future runtime store.
It records bounded receipts and separate pull logs under
`C:\ProgramData\CloudProvisioning\cache-build`, then stops and unregisters the
build service. Fresh preparation refuses an existing runtime data directory;
every operation refuses an existing preparation intent. Inspect the original operation after an observation timeout; do not
delete the intent to trigger another attempt. Allow sufficient remote execution
time for Windows layer extraction. GPU drivers and cloud licensing remain
separate image layers. Use the native Windows platform matcher during pulls;
a bare `--platform windows/amd64` does not carry the host OS version. A successful
pull can leave the selected image not unpacked, as captured in the
[native platform-matching fixture](../harness/e2e/observe/testdata/windows-cache-platform-failure.json).
Require the native unpacked-state gate, independently of pull exit codes.

To extend an unjoined builder's cache, supply the recorded previous recipe and
choose a new operation directory. The extension preserves runtime binaries,
existing image references and their target digests; it rejects removal or
retargeting. It checks the previous cache is idle and fully unpacked before
pulling additions. Validate both recipes on the build host with
`images.windows.cache.validate_extension(previous, recipe, windows_year)`.

```powershell
.\prepare-cache.ps1 -PreviousRecipe .\previous-recipe.json `
  -Recipe .\cache-recipe.json -OperationName cache-infrastructure-v1 `
  -MinimumFreeGiB 30 -PullAuth .\pull-auth.json `
  -UnpackHelper .\cache-unpack.exe -UnpackHelperSHA256 SHA256
```

`MinimumFreeGiB` is a preflight guard, not an estimate of extraction space.
Size the image volume for the chosen Windows layers. Optional `PullAuth` is a
private JSON file with `registry` and `auth` fields for one ECR registry; use a
temporary principal restricted to the recipe's repositories. The build removes
that file and its temporary registry configuration in the operation's cleanup.
If preflight fails before the operation begins, remove any staged credentials
before capture. Require a successful receipt, credential cleanup, independent
cache verification and Sysprep before capturing an extended image. Shutdown
retains the original service-process handle and waits up to 30 seconds for it to
exit before unregistering the service. A stopped/deleted service alone does not
prove that the runtime released its cache. If observation expires, inspect the
original service process before retrying. Preserve failed operation receipts and
perform independent verification after recovery. Fresh-VM reuse remains a
separate qualification gate.

For distribution manifests that request tags, preserve those names explicitly
in the cache instead of changing the distro manifests. Add one `--alias` per
observed tag to the recipe command, with its resolved digest-pinned image also
listed in `--image`:

```sh
python3 images/windows/cache.py --runtime runtime.json --windows-version 2025 \
  --image REGISTRY/IMAGE@sha256:DIGEST \
  --alias REGISTRY/IMAGE:TAG=REGISTRY/IMAGE@sha256:DIGEST \
  --output NEW_RECIPE.json
```

Replace `DIGEST` with the observed 64-character digest. Alias recipes use schema
3; recipes without aliases retain schema 2 and their existing identities.
Aliases must use the same repository as their pinned source. Preparation uses
local tagging without forcing an existing reference. Inspection verifies every
registered name, unpacked state and target digest; AWS image selection requires
that target verification for schema 3. Include an explicitly requested
`TAG@sha256:DIGEST` spelling as another pinned `--image` reference when needed.

Include the distribution's actual pause-image digest and requested tag alongside
workload and infrastructure references. An exact match against an incomplete
recipe cannot prove a complete startup cache. Check fresh-VM events and the actual
pull policy: a local alias does not remove `Always` policy's registry-resolution
requirement. Containerd's
[pinned local-tag implementation](https://github.com/containerd/containerd/blob/v2.3.2/cmd/ctr/commands/images/tag.go)
copies existing metadata without looking up the registry tag. The
[native alias fixtures](../docs/validation/windows-cache-alias-results.json)
cover metadata preservation; the
[Windows 2022](../docs/validation/windows-capi-gpu-startup-cache-canonical-2022-results.json)
and [Windows 2025](../docs/validation/windows-capi-gpu-staged-withdrawal-2025-results.json)
reports cover fresh-worker cache checks and retain their failed traffic gates.

For the standalone builder runtime on `\\.\pipe\cldt-image-cache`, run
`windows/inspect-cache.ps1` on the guest and save its JSON output on the build
host. It reads containerd's ready-image list and checks for workload containers,
tasks, a worker service and known identity files. Evaluate that snapshot with:

```sh
python3 harness/e2e/observe/windows_cache.py \
  --snapshot /path/to/cache-inspection.json \
  --runtime /path/to/runtime.json --windows-version 2022 \
  --image docker.io/your/image@sha256:VERIFIED_DIGEST \
  --output /path/to/cache-readiness.json
```

Repeat `--image` for each intended image. The verifier requires the exact image
set, downloaded and unpacked, in k0s's `k8s.io` namespace and Windows snapshotter,
with the staged runtime hashes. Registered metadata alone is insufficient;
require completed unpacking and cache survival across a runtime restart, as in
the [native readiness fixture](../docs/validation/windows-runtime-cache-results.json).
A passing running-builder snapshot does not replace service shutdown, Sysprep,
or fresh-clone cache verification.

`windows/prepare-k0s.ps1` enables Windows Containers and stages the checksum-pinned
k0s 1.36.2 executable on a fresh Server 2022 or Server 2025 image. Reboot, then
run `windows/verify-k0s.ps1` on each Windows release.
The scripts reject known cluster identity files; prepare images before joining
and never capture a joined worker as a reusable base.

`windows/prepare-worker.ps1` replaces the worker on that unjoined base using a
local executable, an expected SHA-256 and a version. Use the
[complete patched k0s package](../providers/k0s/README.md#build-a-complete-windows-worker)
when testing the Windows Traefik fix. This common layer performs no download and
updates the preparation receipt checked by `verify-k0s.ps1`; cloud adapters can
stage the same artifact before their own capture step. It rejects installed
workers and known cluster identity files.

For large Windows artifacts, use the harness's private file-transfer path rather
than embedding data in userdata or command text. Its PowerShell downloader
suppresses progress reporting during the download, then restores the prior
preference. The [native large-artifact transfer check](../docs/validation/windows-large-artifact-transfer-results.json)
records a 732 MB package transferred through that path; package hash and publisher
verification remain the preparation recipe's responsibility.

[Native preparation evidence](../docs/validation/windows-image-worker-results.json)
records both AWS Windows builders accepting the pinned worker, refusing incorrect
bootstrap versions/hashes, and retaining no joined-worker identity. The same
preparation script rejects live joined workers without changing their executable.
These checks qualify preparation guards; image capture and fresh CAPI boots
have their own acceptance gates.

`windows/prepare-wireguard.ps1` adds the signed WireGuardNT 1.1 DLL, checking the
archive hash, DLL hash and publisher. It retains the SDK's license beside the
DLL. These layers contain no cloud credentials, node certificates or tunnel
keys. Provider-specific agents, licensing, Sysprep and image capture belong to
the cloud adapter.

`windows/prepare-tunnel.ps1` stages the checksum-pinned native service executable.
For AWS, compose these shared layers with
`aws/windows/prepare-bootstrap.ps1`, which bakes the pinned AWS PowerShell
modules used by CAPA’s secure Windows consumer. The
[Windows capture helper](../docs/windows.md#private-aws-image-capture) cleans
run-owned diagnostic state, dispatches EC2Launch Sysprep, captures private AMIs
and authorizes the exact candidates for the isolated CAPA role. Capture does
not qualify first boot, Kubernetes joining or GPU support. See the
[Windows GPU results and remaining gates](../docs/gpu-workers.md) for the tested
AWS configurations; additional cloud capture adapters remain pending.

AWS capture names include the verified tunnel and k0s worker hashes, plus the
driver package hash for GPU variants. A worker-only revision therefore has a
different name from its previous capture. Existing AMIs remain immutable and
recorded for cleanup; capture reuses a recorded image ID instead of requesting
the same image again.

`windows/prepare-nvidia.ps1` installs a locally staged, checksum-pinned and
NVIDIA-signed Windows driver package on an unjoined GPU image builder. The cloud
adapter supplies the package, expected version, license scope and license source;
the common recipe performs no download. Complete an explicit reboot, then run
`windows/verify-nvidia.ps1`. Verification requires the expected version, WDDM mode
and healthy NVIDIA display devices. Its receipt explicitly leaves license
activation and container workloads unvalidated. Do not capture or promote an
image based on successful installer exit alone.

The [AWS GRID 19.5 recipe](aws/windows/nvidia-grid-19.5.json) pins driver 582.53
for initial fractional-L4 testing. AWS currently limits G6f/Gr6f to GRID
18.4–19.5, so copying the `latest` package is not a compatible version-selection
strategy. The pinned object names Server 2022 and 2025; native installation,
reboot, licensing, Sysprep and fresh-worker workloads must pass for each build.
For each Windows release, qualify driver installation, reboot, WDDM/device
health and native licensing, then test plugin registration and an ordinary
container performing Direct3D11 rendering and NVENC encoding. Run the first
workload from the captured cache before any harness image imports. Verify staged
CAPI removal and continuous survivor traffic independently. Successful graphics
execution does not qualify node lifecycle reliability.

The AWS helper uses the same preparation, cleanup, Sysprep and capture phases
for CPU and GPU images. Select `--variant gpu --windows-version 2025` (or `2022`)
for a GPU builder already recorded in `windowsGpuBuilders`. GPU candidates and
receipts are stored in `windowsGpuImageBuilds`; CPU candidates are preserved.
The supplied tunnel executable must match the recorded CPU base image. Revise
the CPU base first when changing worker or tunnel versions.
After installing the driver and rebooting the unjoined builder, run:

```sh
python3 aws/windows_image.py --work-dir "$RUN_DIR" --awsnode "$AWSNODE" \
  --variant gpu --windows-version 2025 --phase prepare --service "$TUNNEL_EXE"
python3 aws/windows_image.py --work-dir "$RUN_DIR" --awsnode "$AWSNODE" \
  --variant gpu --windows-version 2025 --phase generalize
# Wait for EC2Launch to finish Sysprep and stop the builder.
python3 aws/windows_image.py --work-dir "$RUN_DIR" --awsnode "$AWSNODE" \
  --variant gpu --windows-version 2025 --phase capture
```

Run from `harness/e2e` with setup credentials sourced and a valid derived guest
transport session. Preparation reruns native GPU verification, retains the driver
receipts, and removes staged installers and diagnostic state. Capture requires
saved post-reboot WDDM evidence for the selected Windows build. It creates a
private candidate, records it for cleanup, and leaves workload qualification
unchanged. See the [native GPU capture validation](../docs/validation/windows-gpu-capture-results.json)
for completed phases and remaining gates. Once the candidate is available,
use the same selectors with `--phase authorize` to allow its exact AMI in the
isolated CAPA role. Authorization revalidates and retains previously authorized
Windows candidates and the configured Linux AMI; it does not qualify the image.
GPU `revise` requires an explicit changed cache recipe and preserves the recorded
CPU base, worker, tunnel and driver. It retains the previous captured image in
history. Change the CPU base first for a different worker or tunnel; a fresh
CAPI boot and scheduled GPU workloads remain promotion gates.

Create a GPU test worker through the normal CAPI claim path after authorization:

```sh
python3 aws/claim.py --work-dir "$RUN_DIR" --api-server https://10.10.0.10:6443 \
  --name aws-win2025-gpu --windows-version 2025 --variant gpu \
  --instance-type g6f.large
```

The helper selects the GPU AMI, an encrypted root volume at least as large as
both the 60 GiB GPU minimum and the captured image root volume, and the ordinary
Windows bootstrap contract. It creates an `AWSMachineTemplate` and claim;
CAPA provisions the VM. Use `aws/windows_join.py --variant gpu` with the same
Windows version and claim name to observe joining against that image's hashes.
This observer verifies joining, not GPU device allocation or container workloads.


Retain the AWS-restricted package and images privately. This package must not be
reused on another cloud. See [AWS's driver and license requirements](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/nvidia-GRID-driver.html).

The native tunnel probe uses the DLL through its documented API. Its integration
test verifies that an application can create and remove the adapter on both OS
builds. Bake the required binaries and driver into a final worker image before
launching latency-sensitive workloads.


The [Windows WDDM plugin test deployment](probes/windows/device-plugin.yaml)
is restricted to Windows nodes explicitly labelled
`cloud-provisioning.appmana.com/gpu-test=true`. It pins the upstream published
0.0.1 image by digest; the image's Windows 2022 base is not evidence of Windows
2025 compatibility. Observe registration and real per-device allocation on each
OS before qualifying it. The plugin uses HostProcess, but rendering and encoding
acceptance tests must run inside ordinary application containers. This manifest
is test infrastructure, not a validated production deployment.

The [ordinary Windows application probe](probes/windows/README.md) checks hardware
Direct3D rasterization and NVENC encoding of the rendered frames. Its native
execution results are tracked separately from driver and plugin readiness.
